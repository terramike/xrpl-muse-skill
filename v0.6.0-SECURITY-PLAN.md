## Work items

### 1. Fail-closed spend state + reservation cleanup [S]
**Finding (real, verified):** two bugs in the signing path.
- `SpentTracker._load()` (`bin/xrpl_common.py`) treats corrupt JSON or a wrong-shaped state as an empty ledger — limits silently reset after corruption or tampering.
- `cmd_sign()` (`bin/xrpl-sign`) reserves spend *before* `load_seed()`. A missing seed exits via `SystemExit` inside `load_seed`, bypassing `release_reservation` — repeated `--approve` without a seed leaks reservations until entries age out.

**Changes:**
- `_load()`: only a genuinely missing file means empty state. Malformed JSON, truncated files, or wrong structure **abort signing** with explicit recovery instructions (restore the owner-only backup, or reconstruct from `audit.log`, which records every confirmed tx).
- `cmd_sign()`: wrap everything from `try_reserve` through `bind_reservation` in `try/finally` that releases unbound spend *and* mint reservations on **every** exception path, including `SystemExit`, `KeyboardInterrupt`, seed-decode failures, wallet-mismatch, and signing failures.
- **Do NOT move `load_seed()` before the `--approve` check** — in the Muse deployment the vault injects the seed only at genuine human approval time, so reading env earlier would read nothing (and would be a boundary violation).

**Tests:** missing-seed `--approve` leaves zero pending reservations; corrupt/truncated/wrong-type state aborts; injected exceptions at each pre-bind step release cleanly.

### 2. Validated-ledger NFT reads [S]
**Finding (real, verified):** `fetch_nft_offer_entry()` calls `LedgerEntry` and `fetch_nft_meta()` calls `AccountNFTs` with no `ledger_index` — peer servers default to their mutable current ledger.

**Changes:** add `ledger_index="validated"` to both calls, verify the response ledger is validated, and pin the offer-entry and ownership checks to one validated ledger hash/index where feasible.

**Tests:** mocked client asserts `ledger_index="validated"` is sent; unvalidated responses are refused.

### 3. Terminal output sanitization [S]
**Finding (real, verified):** NFT URIs are decoded and printed raw (`nft_sell_offer_report` prints `uri_txt` directly). A malicious URI/title/description can inject ANSI/OSC sequences, newlines, or bidi controls and redraw the ceremony — including a fake price line.

**Changes:** one `safe_terminal_text()` helper in `xrpl_common.py` that escapes all C0/C1 controls, ESC, bidi overrides, and embedded newlines while keeping printable Unicode readable. Apply in `describe_tx()`, `decode_nft_uri()`, `nft_sell_offer_report()`, favorites output, and `xrpl_xrpresso._text()`.

**Tests:** ANSI escapes, OSC-52 clipboard sequences, newlines, and bidi overrides are all neutralized; legitimate Unicode survives.

### 4. Full-hash approval [S]
**Finding (real, verified):** `cmd_sign()` prints and accepts a 16-character proposal-hash prefix (`xrpl-sign --hash {hash[:16]} --approve`). A 64-bit prefix is needless ambiguity in a financial signer.

**Changes:** `--hash` requires the full 64-character hash for signing. Short prefixes remain for read-only listing/search only. Update the ceremony text accordingly.

**Tests:** 16-char prefix to `--hash --approve` is refused; full hash works.

### 5. Pinata: split stage vs. pin-and-propose [M]
**Finding (real, verified):** `cmd_nft_mint()` (`bin/xrpl-trade:486`) calls `pin_artwork(args.file, …)` immediately — **before** any proposal or approval — and `pin_file()` (`bin/xrpl_pin.py:57`) opens any readable path. Pinning is an external write (and an exfiltration vector) that currently happens pre-consent.

**Changes:**
- New `nft-stage`: computes the file hash, builds the metadata, writes a stage record — **zero network calls**.
- New `nft-pin-and-propose`: takes the stage record, pins, then proposes. This is the approval-gated step; the human approves pinning + proposal as one action.
- Restrict source files to an approved media directory (configurable, safe default), open with `O_NOFOLLOW`, enforce MIME and size limits.
- `PINATA_JWT` is never exported into a general agent shell — docs updated to the protected-process/one-operation injection pattern.
- UX note: keep it a two-step flow and say so plainly; do not hide the pin inside a single command again.

**Tests:** a test asserting proposal/stage generation causes zero outbound HTTP requests (socket-level mock); oversized/wrong-MIME/symlink sources refused.

### 6. Issuer-vs-seller ceremony fix [S]
**Finding (real, verified):** the buy ceremony tells the human to "verify the seller is the minter." On secondary sales the seller is the current *owner*; the *Issuer* is the minting identity. `fetch_nft_meta()` doesn't return the Issuer even though `account_nfts` provides it (and NFTokenID decoding exposes it).

**Changes:** return and display the Issuer from `fetch_nft_meta()`; label Owner/seller separately from Issuer/minter in `nft_sell_offer_report()`; rewrite every "verify seller is the minter" string in `README.md`, `SECURITY.md`, `SKILL.md`, `cmd_nft_buy()`, and the report.

**Tests:** report shows distinct owner and issuer lines; ceremony text updated.

### 7. Strict policy schema validation [S–M]
**Finding (real, verified):** `load_policy()` (`bin/xrpl_common.py:1954`) does `merged = dict(DEFAULT_POLICY); merged.update(pol)` — arbitrary JSON overlays defaults, and bad types produce crashes or misleading behavior instead of one fail-closed error.

**Changes:** `validate_policy()` with a strict schema: reject unknown keys; enforce bounded non-negative integers/decimals, known networks, supported transaction types, valid classic addresses, positive TTLs, and internally consistent NFT controls (e.g. value-policy fields only accepted together). One clear fail-closed error on any violation.

**Tests:** unknown keys, wrong types, negative limits, bad addresses, inconsistent NFT controls — each refused with the schema error.

### 8. Docs honesty + deployment profiles [S]
**Changes to `README.md`, `SKILL.md`, `SECURITY.md`:**
- Replace "safe for humans too" with **"testnet-safe by default; mainnet requires the Muse vault signer or an external protected signer with real per-transaction approval."**
- State explicitly that same-user local agents do **not** satisfy the security boundary, even with 0600 files.
- State that NFT listing checks protect neither market value nor ownership unless token/issuer/floor controls are configured (opt-in; see parked item below).
- Clarify that IPFS pinning is an external write — and after item 5, that it happens inside the approved action, not before it.
- Document the three deployment profiles (Muse vault / Xaman-human / autonomous-experimental).
- `install.sh`: install `requirements-locked.txt` (hash-pinned) by default instead of `requirements.txt`; print an explicit testnet-only notice for local same-user installs.
- Commit hygiene going forward: security-relevant changes get honest commit messages; sign release tags.

### 9. Giveaway code gets the same treatment [S]
The audit reviewed only up to v0.5.1 — the giveaway P1/P2 code is new attack surface it never saw: the `--seed-env XRPL_GIVEAWAY_SEED` path, the `giveaway.json` seed fallback in `load_seed()`, the `giveaway gift` ceremony, and `giveaway setup` policy generation.

**Changes:** apply items 1–4 and 7 to the giveaway policy/state paths (they share `SpentTracker` — verify the separate giveaway state file gets the fail-closed `_load` too). Review `giveaway setup`'s seed-storage flow against the item-5 secret-handling standard. Document clearly: vault injection of `XRPL_GIVEAWAY_SEED` is the preferred path; local storage in `giveaway.json` is the deliberate fallback, owner-only, and covered by `check_protected_files`.

### 10. Vault-condition verification [S]
The audit's "conditionally acceptable" for Muse use rests on two claims: (a) the vault truly enforces per-transaction confirmation, (b) the signer code is protected. (a) is verifiable in our setup — every mainnet write has gone through an approval card. (b) gets an explicit verification pass in v0.6.0: confirm what protects `bin/xrpl-sign` and `~/.xrpl/` in the actual deployment, and write the answer down in `SECURITY.md` instead of asserting it.

## Parked (not v0.6.0)

- **Xaman/external signer adapter.** Spec and build later as the community path. The interface contract is already clear from the audit: submit the exact unsigned tx, verify the returned signed blob matches it before considering it approved.
- **NFT value policies as opt-in guardrails** (`allow_sell_offers`, `allowed_nft_issuers`, `allowed_nftoken_ids`, `listing_destination_allowlist`, `min_listing_xrp`, `max_listings_per_day`). Design is sketched; not built, per the direction that NFT creation stays enabled and the ceremony covers the Muse deployment.
- **Dedicated signer service / OS identity** (the real fix for the same-user problem). Acknowledged, out of scope under Muse-only positioning; documented instead of built.

## Objections & concerns (stated before building, per standing rule)

1. **Fail-closed state needs a recovery path, or a corrupt disk bricks signing with no recourse.** Mitigation is in item 1: abort message must print exact recovery steps (owner-only backup; `audit.log` reconstruction). The audit log is the source of truth — confirm it records everything needed for reconstruction before relying on it.
2. **The Pinata split changes UX from one command to two.** Accepted deliberately — the current one-command flow is exactly the vulnerability. The plan says so in the docs instead of hiding it.
3. **Sanitization vs. readability.** Over-aggressive escaping makes legitimate metadata ugly and trains the human to ignore the ceremony. The helper keeps printable Unicode and only neutralizes control/escape/bidi — tests pin this balance.
4. **Scope discipline.** Every item above is S–M and verified against the local tree. If anything grows during the build (especially item 5's secret handling), it gets split out and re-approved rather than sprawling.
